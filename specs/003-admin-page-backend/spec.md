## User Scenarios & Testing *(mandatory)*

### User Story 1 - 운영 지표 대시보드 (Priority: P1)

관리자가 어드민 페이지에 접속하면 서비스의 핵심 운영 지표를 한 화면에서 확인할 수 있다:
기간별 검색 사용량(지문/허밍 모드별), 매칭 성공률, 검색 응답 시간 p95(KR2), 검색
완료율(KR3), 방문·가입 추이, 검색 실패 사유 분포. 기간(오늘/최근 7일/최근 30일/직접 지정)을
바꿔가며 추이를 볼 수 있다. 관리자가 아닌 사용자는 이 기능에 접근할 수 없다.

**Why this priority**: Q3 OKR(KR1 매칭률·KR2 응답 시간·KR3 완료율)이 프로젝트의 판단
기준인데, 현재는 운영자가 데이터 저장소에 수작업 질의를 실행해야만 값을 알 수 있다.
지표 확인 비용이 높으면 측정 기반 의사결정(원칙 III)이 무너진다. 어드민의 존재 이유
1순위다.

**Independent Test**: 관리자 계정으로 지표 조회 기능만 붙여도 독립적으로 가치를
전달한다 — 운영 데이터가 이미 쌓여 있으므로 기간을 바꿔 조회하고, 문서화된 기존 지표
산출 기준과 값이 일치하는지 대조하는 것만으로 검증 가능.

**Acceptance Scenarios**:

1. **Given** 관리자 역할의 사용자가 로그인해 있다, **When** 어드민 지표 화면에 진입한다,
   **Then** 선택한 기간의 검색 사용량·매칭 성공률·응답 시간 p95·검색 완료율·실패 사유
   분포가 표시된다.
2. **Given** 지표 화면에 있다, **When** 기간을 "최근 7일"에서 "최근 30일"로 바꾼다,
   **Then** 모든 지표가 해당 기간 기준으로 다시 계산되어 표시된다.
3. **Given** 선택한 기간에 수집된 데이터가 없다, **When** 지표를 조회한다, **Then** 오류가
   아닌 "데이터 없음"(0 또는 빈 상태)으로 표시된다.
4. **Given** 일반 사용자(또는 게스트)다, **When** 관리자 기능에 접근을 시도한다, **Then**
   접근이 거부되고 일반 사용자 경험에는 아무 영향이 없다.

### User Story 2 - 곡 데이터 정정 (Priority: P2)

관리자가 서비스에 캐시된 곡 목록을 제목·아티스트로 검색해 살펴보고, 잘못된 곡 정보
(제목·아티스트·앨범·재생 링크·커버 이미지 주소)를 화면에서 바로 정정하거나, 문제가 있는
항목을 삭제할 수 있다. 관리자가 정정한 곡은 이후 검색 파이프라인의 자동 저장이 다시
덮어쓰지 않는다.

**Why this priority**: 곡 메타 오류는 실제로 발생한 운영 문제다(유튜브 링크 누락·오염
사례, 오매칭 진단 진행 중). 재생 수단이 유튜브 링크뿐이므로 링크 오류는 곧 "듣기 불가"이며,
현재는 데이터 저장소를 직접 수정하는 방법밖에 없다. 사용자 피해로 직결되는 데이터를
고치는 도구라는 점에서 지표 다음 순위다.

**Independent Test**: 곡 관리 기능만 붙여도 독립 검증 가능 — 캐시된 곡을 검색해 재생
링크를 수정한 뒤, 사용자 화면에서 해당 곡의 듣기 동작이 바뀐 값으로 동작하는지 확인.

**Acceptance Scenarios**:

1. **Given** 관리자가 곡 관리 화면에 있다, **When** 제목 또는 아티스트로 검색한다,
   **Then** 일치하는 곡 목록이 페이지 단위로 표시된다.
2. **Given** 재생 링크가 잘못된 곡을 찾았다, **When** 재생 링크(영상 식별자)를 수정하고
   저장한다, **Then** 이후 사용자 화면의 해당 곡 듣기가 수정된 링크로 동작한다.
3. **Given** 관리자가 어떤 곡의 정보를 수동 정정했다, **When** 이후 검색 파이프라인이 같은
   곡을 다시 인식한다, **Then** 자동 저장이 관리자의 정정 내용을 덮어쓰지 않는다.
4. **Given** 사용자의 저장(즐겨찾기·플레이리스트·검색 기록)이 참조 중인 곡이다, **When**
   관리자가 삭제를 시도한다, **Then** 삭제가 차단되고 참조 현황이 안내된다.

### User Story 3 - 사용자·콘텐츠 조회와 모더레이션 (Priority: P3)

관리자가 가입 사용자 목록을 이메일·닉네임으로 검색해 가입일과 활동 요약(검색 기록 수·
즐겨찾기 수·플레이리스트 수·리뷰 작성 여부)을 확인할 수 있다. 부적절한 리뷰·댓글을
삭제하고, 부적절한 공개 플레이리스트를 비공개로 전환할 수 있다.

**Why this priority**: PRD가 예고한 관리자 책무(리뷰 관리)이지만, 현재 사용자 규모가
작고 신고 기능도 없어 긴급하지 않다. 커뮤니티 노출 면적(공개 플레이리스트·댓글)이
커지기 전에 최소한의 조치 수단만 갖춘다.

**Independent Test**: 테스트 계정으로 리뷰·댓글·공개 플레이리스트를 만든 뒤, 관리자
계정으로 각각 삭제·비공개 전환하고 일반 사용자 화면에서 사라졌는지 확인하는 것으로
독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 관리자가 사용자 관리 화면에 있다, **When** 이메일 또는 닉네임으로 검색한다,
   **Then** 일치하는 사용자의 가입일과 활동 요약이 표시된다.
2. **Given** 부적절한 리뷰가 있다, **When** 관리자가 삭제한다, **Then** 리뷰 목록에서
   사라지고, 작성자는 1인 1리뷰 규칙에 따라 새 리뷰를 다시 작성할 수 있다.
3. **Given** 부적절한 공개 플레이리스트가 있다, **When** 관리자가 비공개로 전환한다,
   **Then** 커뮤니티 탐색에서 사라지고 소유자 본인은 계속 볼 수 있다.
4. **Given** 대댓글이 달린 부적절한 댓글이 있다, **When** 관리자가 그 댓글을 삭제한다,
   **Then** 대댓글도 함께 삭제된다(작성자 본인이 삭제할 때와 동일한 기존 규칙).

---

### Edge Cases

- 관리자 역할이 회수된 사용자가 이미 로그인 상태라면? → 다음 관리자 기능 요청부터
  거부된다(역할 판정은 항상 현재 저장된 역할 기준).
- 관리자 정정과 검색 파이프라인의 자동 저장이 같은 곡에 동시에 일어나면? → 수동 정정
  보호가 우선한다(US2-3).
- 지표 조회 기간을 수년 단위로 넓게 지정하면? → 조회는 동작하되, 무거운 지표 조회가
  일반 사용자의 검색 응답 시간(KR2)을 저해해서는 안 된다.
- 리뷰가 관리자에 의해 삭제된 사용자가 재작성하면? → 정상 작성된다(1인 1리뷰의 "1건"은
  현존 리뷰 기준).
- 곡 삭제가 차단된 경우 관리자가 취할 수 있는 대안은? → 곡 정보 정정(US2-2)으로 유도.
- 관리자 기능 도입 후에도 게스트 익명성(세션 식별자만, IP 미저장)은 그대로 유지되어야
  한다 — 어드민 화면이 게스트를 개인 식별하는 수단이 되어서는 안 된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 관리자 역할이 부여된 로그인 사용자만 관리자 기능을 이용할 수 있어야 한다.
  게스트·일반 사용자의 접근은 거부되어야 하며, 관리자 기능의 존재가 일반 사용자 경험에
  영향을 주어서는 안 된다.
- **FR-002** *(2026-07-22 개정 — 프론트 계약 §5 채택)*: 최초 관리자 지정(부트스트랩)은
  운영자가 데이터 저장소에서 직접 수행한다. 이후 역할 변경(승격·해제)은 **관리자 전용
  기능으로만** 가능하다 — 일반 사용자가 스스로 관리자로 승격할 수 있는 경로가 있어서는
  안 되고, 자기 자신의 관리자 권한 해제는 차단한다(관리자 부재 사태 방지). 모든 역할
  변경은 감사 기록 대상이다(FR-011).
- **FR-003**: 시스템은 관리자에게 다음 운영 지표를 제공해야 한다 — 기간별 검색 요청
  수(모드별 분해), 매칭 성공률, 검색 응답 시간 p95, 검색 완료율(결과 확인 세션 ÷ 방문
  세션), 방문·가입 추이, 검색 실패 사유 분포.
- **FR-004**: 모든 지표는 기간 필터(오늘/최근 7일/최근 30일/직접 지정)로 조회할 수 있어야
  하며, 지표 값은 문서화된 기존 산출 기준과 동일한 정의를 따라야 한다.
- **FR-005**: 관리자는 캐시된 곡을 제목·아티스트로 검색하고 페이지 단위로 살펴보고 상세
  정보를 확인할 수 있어야 한다.
- **FR-006**: 관리자는 곡의 제목·아티스트·앨범·발매일·재생 영상 식별자·커버 이미지 주소를
  수정할 수 있어야 한다(부분 수정 — 담긴 필드만 반영, 빈 값 전송은 비우기). 수정은 데이터
  정본 규칙을 따라야 한다 — 재생 링크는 영상 식별자가 정본이고, 커버는 핫링크 주소
  문자열만 저장한다.
- **FR-007**: 관리자가 수동 정정한 곡은 이후 검색 파이프라인의 자동 저장이 덮어쓰지 않아야
  한다.
- **FR-008**: 곡 삭제는 사용자의 저장(즐겨찾기·플레이리스트·검색 기록)이 참조하지 않는
  경우에만 허용되며, 참조 중이면 차단하고 참조 현황을 안내해야 한다.
- **FR-009**: 관리자는 가입 사용자를 이메일·닉네임으로 검색하고, 가입일과 활동 요약(검색
  기록 수·즐겨찾기 수·플레이리스트 수·리뷰 작성 여부)을 확인할 수 있어야 한다.
- **FR-010**: 관리자는 리뷰·댓글을 삭제하고 공개 플레이리스트를 비공개로 전환할 수 있어야
  한다. 삭제·전환은 대상 소유자의 다른 데이터에 영향을 주지 않아야 한다. 단, 댓글 삭제 시
  대댓글은 함께 삭제된다(작성자 본인 삭제와 동일한 기존 규칙).
- **FR-011**: 관리자의 모든 변경 작업(정정·삭제·비공개 전환)은 수행자·시각·작업 종류·대상·
  변경 내용이 감사 기록으로 남아야 한다.
- **FR-012**: 관리자 기능 추가로 기존 사용자 기능의 계약·동작이 변경되어서는 안 된다.
  관리자 기능은 기존 기능과 독립된 신규 영역으로만 추가한다.
- **FR-013**: 관리자에게 노출되는 개인 정보는 서비스가 이미 보유한 프로필 정보(이메일·
  닉네임·가입일)로 한정한다. 게스트 익명성(세션 식별자만, IP 미저장)은 그대로 유지한다.
- **FR-014**: 관리자 지표 조회가 일반 사용자의 검색 응답 성능(KR2)을 저해해서는 안 된다.

### Key Entities

- **관리자 역할**: 사용자 프로필에 이미 존재하는 역할 속성. 기본값은 일반 사용자이며,
  관리자 지정은 운영자의 수동 조치로만 이루어진다.
- **운영 지표**: 기존에 수집 중인 행동 계측 기록(방문·검색 시작/결과/실패·검색 처리
  타이밍)에서 산출되는 파생 값. 본 기능은 새 계측을 추가하지 않고 기존 원천만 읽는다.
- **곡(캐시)**: 인식 결과로 축적된 곡 정보. 본 기능에서 "수동 정정됨" 표시가 추가되어
  자동 갱신으로부터 보호되는 상태를 가진다.
- **감사 기록**: 관리자 변경 작업의 이력(수행자·시각·작업 종류·대상·변경 내용). 본 기능이
  새로 도입하는 유일한 기록이다.
- **사용자·리뷰·댓글·플레이리스트**: 기존 도메인 데이터. 본 기능은 조회와 최소한의 조치
  (삭제·비공개 전환)만 수행하며 구조를 바꾸지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 관리자가 핵심 운영 지표(응답 시간 p95·검색 완료율·매칭 성공률)를 별도 도구나
  수작업 질의 없이 어드민 화면 진입 후 1분 이내에 확인할 수 있다.
- **SC-002**: 잘못된 곡 정보를 발견한 시점부터 정정 완료까지 2분 이내에 처리할 수 있다
  (현재: 데이터 저장소 콘솔 직접 수정).
- **SC-003**: 비관리자(게스트·일반 사용자)의 관리자 기능 접근 시도는 100% 차단된다.
- **SC-004**: 관리자의 변경 작업은 100% 감사 기록으로 남는다(누락 0건).
- **SC-005**: 관리자 기능 출시 전후로 기존 사용자 시나리오(검색·저장·조회)의 회귀가 0건이다.
- **SC-006**: 대시보드 지표 값이 동일 기간 기준으로 문서화된 기존 산출 기준의 결과와
  일치한다.

## Assumptions

- **관리자는 초기 1인(운영자 본인)**이다. 역할 세분화(RBAC 확장)는 후속 범위로 미룬다.
  *(2026-07-22 개정)* 앱 내 역할 변경은 프론트 계약 §5 채택으로 범위에 포함되었다 —
  관리자 전용 + 자기 해제 차단(FR-002). 최초 부트스트랩은 여전히 데이터 저장소 수동 지정.
- **지표 원천은 기존 행동 계측 기록으로 한정**한다. 새 계측 없이 산출 가능한 지표만 1차
  범위이며, 매칭률(KR1)의 정밀 실측(테스트 곡 셋)은 기존 수동 스크립트 체계를 유지한다.
- **신고 관리 제외**: 사용자 측에 신고 기능 자체가 없으므로 PRD §14의 "신고 관리"는 신고
  기능이 생긴 후의 후속 범위다.
- **프론트엔드 분리 진행**: 관리자 화면은 별도 작업 트리에서 병행 구현한다. 본 기능은
  계약(무엇을 조회·변경할 수 있는가)을 먼저 확정해 실행 PRD 문서에 반영하고, 화면 작업은
  확정된 계약을 소비한다. "API와 화면을 한 브랜치·한 PR로"(원칙 II) 원칙의 예외이며,
  계획 단계의 Complexity Tracking에 정당화 사유를 기록한다.
- **병행 작업과의 충돌 최소화**: 진행 중인 다른 기능 브랜치(AI 자연어 폴백 검색, spec 002)와
  병합 충돌을 피하기 위해, 공용 영역(보안 설정·공통 예외 처리·기존 도메인 계약)의 변경 없이
  신규 영역 추가만으로 구현 가능하도록 범위를 정의했다(FR-012). AI 검색 관련 지표·사용량
  관리는 spec 002 병합 후 후속으로 다룬다.
- **관리자 화면은 데스크톱 사용을 전제**로 한다(모바일 최적화는 후속). 화면 구성의 상세는
  프론트엔드 실행 PRD에서 다룬다.
