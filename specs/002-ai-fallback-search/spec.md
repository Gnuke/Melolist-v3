# Feature Specification: AI 자연어 폴백 검색

**Feature Branch**: `002-ai-fallback-search`

**Created**: 2026-07-21

**Status**: Draft

**Input**: User description: "현재 프로젝트에 ai를 붙여서 자연어 폴백 검색 기능을 추가하려고 해. 분석해줘."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 검색 실패 후 말로 이어서 찾기 (Priority: P1)

허밍/녹음 검색이 곡을 찾지 못했을 때, 사용자는 결과 화면에서 바로 "말로 설명해서 찾기"로
이어갈 수 있다. 기억나는 조각 — 가사 일부, 분위기, 들었던 상황("여자 보컬 드라마 OST,
가사에 '바람'이 들어감") — 을 자유 텍스트로 입력하면, 후보 곡 목록(최대 5곡)이 기존 검색
결과와 같은 카드 형태(제목·아티스트·커버·재생 링크)로 표시된다. 게스트도 로그인 없이
사용할 수 있다.

**Why this priority**: 현재 확인된 최대 품질 약점은 허밍 인식 실패(외부 인식 서비스의
허밍 커버리지 한계)다. 실패한 검색은 지금 막다른 길로 끝나며, 사용자가 앱을 떠나는
지점이다. 이 폴백은 "실패로 끝나던 세션"을 "곡을 찾은 세션"으로 전환하는 유일한 수단이고,
OKR의 O(게스트가 흥얼거린 곡을 찾아내는 경험)를 실패 경로에서 지켜낸다.

**Independent Test**: 인식 실패가 나는 오디오(또는 mock 실패 시나리오)로 검색 → 결과
화면에서 폴백 진입 → 텍스트 입력 → 후보 목록 표시 확인. 이 흐름만으로 독립 검증 가능하며
그 자체로 가치를 전달한다.

**Acceptance Scenarios**:

1. **Given** 허밍 검색이 미매칭으로 끝난 결과 화면이다, **When** 폴백 진입점을 눌러
   곡에 대한 설명을 입력하고 검색한다, **Then** 후보 곡 목록(1~5곡)이 기존 검색 결과와
   동일한 카드 형태로 표시된다.
2. **Given** 후보 목록이 표시되어 있다, **When** 후보 중 하나를 선택한다, **Then** 기존
   검색 결과와 동일하게 재생 링크 이동·즐겨찾기·플레이리스트 담기(저장은 로그인 필요
   규칙 동일)가 가능하다.
3. **Given** 게스트(비로그인) 상태다, **When** 폴백 검색을 사용한다, **Then** 로그인
   요구 없이 후보 확인까지 완료할 수 있다.
4. **Given** 폴백 검색이 진행 중이다, **When** 처리에 시간이 걸린다, **Then** 진행 중
   상태가 표시되고 사용자는 언제든 취소하고 이전 화면으로 돌아갈 수 있다.

---

### User Story 2 - 잘못 매칭된 결과에서 폴백으로 전환 (Priority: P2)

허밍 검색이 곡을 반환했지만 사용자가 찾던 곡이 아닐 때("이 곡이 아니에요"), 결과 화면에서
같은 폴백 검색으로 전환할 수 있다. 사용자는 처음부터 다시 녹음하지 않고 텍스트 설명으로
이어간다.

**Why this priority**: 오매칭 진단 결과, 낮은 신뢰도 매칭은 틀린 곡을 반환하는 경우가
있다. 미매칭(US1)보다 빈도는 낮지만, "틀린 곡을 보여주고 끝"은 미매칭보다 신뢰를 더
해친다. US1의 진입점·화면을 재사용하므로 증분 비용이 작다.

**Independent Test**: 매칭 성공 결과 화면(또는 mock 성공 시나리오)에서 "찾는 곡이
아닌가요?" 진입점을 눌러 폴백 흐름이 US1과 동일하게 동작하는지 확인.

**Acceptance Scenarios**:

1. **Given** 허밍 검색이 곡을 반환한 결과 화면이다, **When** "찾는 곡이 아닌가요?"
   진입점을 누른다, **Then** US1과 동일한 폴백 입력 화면으로 이동한다.
2. **Given** 폴백 입력 화면으로 전환했다, **When** 설명을 입력해 후보를 받는다,
   **Then** 원래의 (틀린) 매칭 결과로 언제든 돌아갈 수 있다.

---

### User Story 3 - 후보가 없거나 아닐 때 보완해서 재시도 (Priority: P3)

후보 목록에 찾는 곡이 없으면, 사용자는 입력을 보완(추가 단서 입력)해서 같은 화면에서
다시 시도할 수 있다. 시스템이 후보를 전혀 찾지 못한 경우에는 그 사실과 함께 어떤 단서를
추가하면 좋은지(가사 일부, 발표 시기, 장르 등) 안내한다.

**Why this priority**: 첫 시도 성공률이 완벽할 수 없으므로 재시도 루프가 있어야 폴백의
실질 성공률이 올라간다. 다만 US1이 없으면 존재할 수 없는 보조 흐름이므로 P3.

**Independent Test**: 후보를 찾지 못하는 입력(또는 mock 무후보 시나리오)으로 검색 →
안내 문구 확인 → 단서를 추가해 재시도 → 새 후보 표시 확인.

**Acceptance Scenarios**:

1. **Given** 후보를 찾지 못했다, **When** 결과가 표시된다, **Then** 오류가 아닌 안내
   (추가하면 좋은 단서 예시 포함)가 표시되고 입력을 수정해 재시도할 수 있다.
2. **Given** 후보 목록이 표시되었지만 찾는 곡이 없다, **When** 입력을 보완해 다시
   검색한다, **Then** 이전 입력이 유지된 상태에서 수정할 수 있고 새 후보가 표시된다.

---

### Edge Cases

- 입력이 비었거나 의미를 파악할 수 없을 만큼 짧으면? → 검색을 실행하지 않고 입력 안내를
  표시한다.
- 외부 AI 서비스가 응답하지 않거나 제한 시간을 초과하면? → 이해할 수 있는 안내와 함께
  재시도를 제공하고, 앱의 다른 기능은 영향받지 않는다.
- 후보 곡의 재생 링크를 확인할 수 없으면? → 후보는 표시하되 링크 없이 제공한다(기존
  "링크 미해석 곡 저장 허용" 정책과 동일).
- 이용 한도를 초과한 사용자가 다시 시도하면? → 한도 초과 사실과 다시 가능해지는 시점을
  안내한다.
- 곡 찾기와 무관한 입력(잡담·부적절한 내용)이 들어오면? → 곡 후보를 반환하지 못한 경우와
  동일하게 "찾지 못함 + 단서 안내"로 처리한다(별도 대화 기능이 아님).
- 검색 도중 사용자가 취소하면? → 진행 중 요청은 중단되고 결과·검색 기록에 반영되지
  않으며, 사용자는 이전 화면으로 복귀한다. 단, 요청은 접수 시점에 이용 한도에
  집계된다(취소 반복으로 한도를 우회하는 남용 방지).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 허밍/녹음 검색이 미매칭으로 끝난 결과 화면에서 자연어 폴백 검색 진입점을
  제공해야 한다. 게스트를 포함한 모든 사용자가 사용할 수 있어야 한다.
- **FR-002**: 매칭 결과가 표시된 화면에도 "찾는 곡이 아닌가요?" 형태의 폴백 진입점을
  제공해야 한다.
- **FR-003**: 사용자는 자유 텍스트(가사 조각·분위기·상황·아티스트 추정 등)로 곡을 설명해
  검색할 수 있어야 한다. 입력은 최소/최대 길이 제한을 가지며, 범위를 벗어나면 실행 전에
  안내한다.
- **FR-004**: 시스템은 입력당 후보 곡을 최대 5곡까지 반환하고, 각 후보를 기존 검색 결과와
  동일한 정보 구성(제목·아티스트·커버 이미지·재생 링크)으로 표시해야 한다. 재생 링크를
  확인할 수 없는 후보는 링크 없이 표시할 수 있다.
- **FR-005**: 후보 선택 시 기존 검색 결과와 동일한 후속 행동(재생 링크 이동, 즐겨찾기,
  플레이리스트 담기)이 가능해야 하며, 저장 계열 행동의 로그인 요구 규칙은 기존과 동일하게
  적용된다.
- **FR-006**: 폴백 검색으로 확인(선택)한 곡은 기존 검색과 구분 가능한 방식으로 검색
  기록에 남아야 한다(로그인 사용자에 한함 — 기존 기록 정책과 동일).
- **FR-007**: 검색 진행 중 상태를 표시하고, 사용자가 취소할 수 있어야 한다. 제한 시간을
  초과한 요청은 실패로 처리하고 재시도를 안내한다.
- **FR-008**: 후보를 찾지 못한 경우 오류가 아닌 안내(보완하면 좋은 단서 예시 포함)를
  표시하고, 이전 입력을 유지한 채 수정·재시도할 수 있어야 한다.
- **FR-009**: 폴백 검색의 요청·응답·후보 채택(선택한 후보의 순위 포함)·실패·취소를
  이벤트로 수집하고, 요청별 구간 소요 시간을 기록해야 한다. 이 계측은 본 기능과 같은
  마일스톤 안에서 함께 출고한다.
- **FR-010**: 사용자(게스트 포함)별 이용 한도를 두어 외부 AI 호출 비용과 남용을 통제해야
  한다. 한도 초과 시 이해할 수 있는 안내를 표시한다.
- **FR-011**: 외부 AI 서비스 인증 정보는 서버에만 존재해야 하며 사용자 단말에 노출되지
  않아야 한다.
- **FR-012**: 폴백 검색은 텍스트만 외부 AI 서비스에 전달한다. 녹음 오디오 원본은 폴백
  경로에서도 전송·저장하지 않는다(오디오 비저장 원칙 유지).
- **FR-013**: 외부 AI 서비스를 실제로 호출하지 않고도 폴백 흐름 전체(성공·무후보·실패·
  지연 시나리오)를 검증할 수 있는 수단을 함께 제공해야 한다.

### Key Entities

- **폴백 질의**: 사용자가 입력한 설명 텍스트와 그 처리 결과(후보 수, 소요 시간, 채택
  여부·채택 순위, 실패/취소 여부). 지표 산출의 원천이 된다.
- **후보 곡**: 폴백 검색이 반환한 곡. 기존 곡 데이터와 동일한 정본 규칙(재생 링크 식별자
  중심, 커버는 핫링크 주소만)을 따르며, 채택 시 기존 곡 데이터로 합류한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 허밍/녹음 검색이 미매칭으로 끝난 세션 중 30% 이상이 폴백 검색을 시도한다.
- **SC-002**: 폴백 검색 시도(재시도 포함) 중 40% 이상에서 사용자가 후보 곡을 선택한다.
- **SC-003**: 폴백 검색 요청의 95%가 15초 이내에 후보 목록 또는 무후보 안내를 표시한다.
- **SC-004**: 폴백 도입 후, 검색 실패로 끝나던 세션의 25% 이상이 곡 확인(후보 선택)으로
  전환된다.
- **SC-005**: 폴백 검색의 요청 수·채택률·소요 시간·실패율을 운영 데이터에서 조회 가능한
  상태로 출고한다(도입 시점부터 원천 데이터 수집).

## Assumptions

- **폴백 전용 범위**: 이번 기능은 허밍/녹음 검색의 실패·오매칭 경로에서 진입하는 폴백으로
  한정한다. 홈 화면에서 바로 시작하는 독립 텍스트 검색은 이번 범위에 포함하지 않는다
  (진입점만 추가하면 재사용 가능한 구조로 만들되, 출시 범위는 폴백).
- **대화가 아닌 검색**: 폴백은 1회 입력 → 후보 반환의 검색 상호작용이다. 여러 턴을
  이어가는 대화형 인터페이스는 범위 밖이다(재시도는 입력 수정으로 처리).
- **후보 상한 5곡**: 선택 부담과 화면 구성을 고려한 기본값이다.
- **이용 한도 기본값**: 게스트·로그인 사용자 모두에게 일일 한도를 두되, 구체 수치는
  계획 단계에서 외부 AI 서비스 비용 단가와 함께 확정한다.
- **기록 정책 재사용**: 폴백으로 확인한 곡의 기록·저장은 기존 검색 기록/즐겨찾기 정책
  (로그인 필요, 게스트 미기록)을 그대로 따른다.
- **외부 AI 서비스 의존**: 곡 식별에 외부 AI 서비스를 사용하며, 해당 서비스 장애 시 폴백
  기능만 우아하게 실패하고 기존 검색은 영향받지 않는다.
- **성능 목표의 성격**: 폴백은 이미 실패한 검색의 구제 경로이므로, 기존 검색의 응답 목표
  (허밍 p95)보다 완화된 별도 목표(SC-003)를 적용한다.
