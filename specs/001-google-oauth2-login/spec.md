# Feature Specification: Google 로그인 (OAuth2)

**Feature Branch**: `001-google-oauth2-login`

**Created**: 2026-07-13

**Status**: Draft

**Input**: User description: "google login을 위해서 OAuth2를 붙일거야. 추가해서 specify 진행해줘"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Google 계정으로 로그인 (Priority: P1)

게스트 사용자가 로그인 화면에서 "Google로 계속하기"를 누르면 Google 계정 선택·동의
화면을 거쳐 앱으로 돌아오고, 로그인된 상태가 된다. 처음 로그인하는 사용자는 별도 가입
절차 없이 즉시 계정이 만들어진다(JIT 가입 — 확정 정책).

**Why this priority**: 로그인은 저장(즐겨찾기·검색 기록·플레이리스트)과 커뮤니티 기능의
전제 조건이다. 현재 로그인 화면과 버튼은 존재하지만 실제 인증이 완성되지 않아, 로그인이
필요한 모든 후속 기능(M3·M4)이 막혀 있다.

**Independent Test**: 게스트 상태에서 로그인 화면에 진입해 Google 계정으로 인증을
완료하고, 앱 내에서 로그인 상태(내 프로필 표시)를 확인하는 것만으로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 게스트가 로그인 화면에 있다, **When** "Google로 계속하기"를 눌러 Google
   계정 인증을 완료한다, **Then** 앱으로 복귀하고 로그인 상태가 표시된다.
2. **Given** Google로 처음 로그인하는 사용자다, **When** 인증을 완료한다, **Then**
   어떤 추가 입력도 없이 계정과 프로필이 자동 생성된다.
3. **Given** 이전에 Google로 로그인한 적이 있는 사용자다, **When** 다시 로그인한다,
   **Then** 항상 동일한 계정으로 연결된다(중복 계정 생성 없음).

---

### User Story 2 - 로그인 후 하던 일 이어가기 (Priority: P2)

검색 결과에서 즐겨찾기를 누른 게스트에게 로그인 유도가 표시된다. 여기서 로그인을
진행한 사용자는 로그인 완료 후 로그인을 시작했던 맥락으로 돌아와 이용을 이어갈 수
있어야 한다. 인증을 취소하거나 실패해도 앱 이용이 중단되지 않아야 한다.

**Why this priority**: OKR의 목표는 "게스트가 30초 안에 곡을 찾는 경험"이다. 로그인이
그 흐름을 끊고 처음부터 다시 시작하게 만들면, 로그인 유도가 오히려 핵심 경험을
해치게 된다.

**Independent Test**: 검색 결과 화면에서 즐겨찾기 → 로그인 유도 → 로그인 완료 후 복귀
위치 확인. 별도로 Google 동의 화면에서 취소 후 앱 상태 확인.

**Acceptance Scenarios**:

1. **Given** 검색 결과에서 즐겨찾기를 눌러 로그인 유도로 진입했다, **When** 로그인을
   완료한다, **Then** 홈이 아닌, 로그인을 시작한 화면(또는 유도한 기능)으로 복귀한다.
2. **Given** Google 동의 화면까지 진행했다, **When** 취소하고 돌아온다, **Then** 오류가
   아닌 정상 상태로 로그인 화면(또는 이전 화면)에 복귀하고 재시도할 수 있다.
3. **Given** 인증 도중 오류가 발생했다, **When** 앱으로 복귀한다, **Then** 이해할 수
   있는 안내가 표시되고 게스트로서 검색 등 핵심 기능을 계속 사용할 수 있다.

---

### User Story 3 - 세션 유지와 로그아웃 (Priority: P3)

로그인한 사용자는 브라우저를 닫았다가 다시 방문해도 로그인 상태가 유지된다.
원할 때 로그아웃하여 게스트 상태로 돌아갈 수 있다.

**Why this priority**: 재방문율(D7/D30)이 KPI다. 방문마다 재로그인을 요구하면 저장
기능의 가치가 사라진다. 로그아웃은 로그인의 대칭 기능으로 함께 제공되어야 한다.

**Independent Test**: 로그인 → 탭 종료 → 재방문 시 로그인 유지 확인. 로그아웃 후
로그인 필요 기능이 다시 로그인 유도로 동작하는지 확인.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자다, **When** 브라우저를 닫고 다시 방문한다, **Then**
   재로그인 없이 로그인 상태가 유지된다.
2. **Given** 로그인한 사용자다, **When** 로그아웃한다, **Then** 게스트 상태로 전환되고
   로그인 필요 기능은 다시 로그인 유도로 동작한다.
3. **Given** 세션이 만료 시점에 가까워졌다, **When** 앱을 계속 사용한다, **Then**
   사용자 개입 없이 세션이 자동 갱신된다. 갱신이 불가능하면 게스트로 전환되고
   재로그인이 유도된다.

---

### Edge Cases

- Google 동의 화면에서 사용자가 취소하면? → 오류가 아닌 정상 흐름으로 처리하고 이전
  화면으로 복귀, 재시도 가능해야 한다.
- 인증 도중 네트워크 오류·제공자 장애가 나면? → 사용자 친화적 안내와 함께 게스트
  상태로 복귀하고, 핵심 기능(검색) 이용은 계속 가능해야 한다.
- 동일한 이메일을 쓰는 기존 계정이 이미 있으면? → 별도 절차 없이 같은 계정으로
  연결되어야 하며 중복 계정이 생기지 않아야 한다.
- 최초 로그인 직후 프로필 자동 생성이 일시적으로 실패하면? → 로그인 자체는 유지하고,
  다음 이용 시 자동으로 복구(재생성)되어야 한다. 사용자에게 기술 오류를 노출하지 않는다.
- 이미 로그인한 사용자가 로그인 화면에 직접 접근하면? → 로그인 UI 대신 홈(또는 이전
  화면)으로 안내한다.
- 로그인 과정에서 앱을 이탈(탭 종료)하면? → 다음 방문 시 게스트 상태로 정상 동작해야
  한다(어중간한 세션 상태 금지).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 게스트는 로그인 화면에서 Google 계정으로 로그인을 시작할 수 있어야 한다.
- **FR-002**: 최초 로그인 시 별도 가입 폼 없이 계정과 프로필이 자동 생성되어야 한다
  (JIT 가입 — PRD 확정 정책).
- **FR-003**: 재로그인 시 항상 동일 계정으로 연결되어야 하며, 동일(검증된) 이메일의
  기존 계정이 있는 경우에도 중복 계정이 생성되지 않아야 한다.
- **FR-004**: 로그인 완료 후 사용자는 홈이 아닌, 로그인을 시작한 화면(또는 로그인을
  유도한 기능의 맥락)으로 복귀해야 한다.
- **FR-005**: 사용자가 인증을 취소하거나 인증이 실패한 경우, 오류가 아닌 안내와 함께
  이전 상태로 복귀하고 재시도할 수 있어야 한다. 게스트 핵심 기능은 계속 동작해야 한다.
- **FR-006**: 로그인 상태에서는 로그인 필요 기능(즐겨찾기, 검색 기록 저장, 이후
  리뷰·플레이리스트)이 활성화되어야 한다.
- **FR-007**: 재방문 시 로그인 상태가 유지되어야 하며, 세션 갱신은 사용자 개입 없이
  자동으로 이루어져야 한다.
- **FR-008**: 로그인한 사용자는 로그아웃할 수 있어야 하며, 로그아웃 시 게스트 상태로
  전환되어야 한다.
- **FR-009**: 로그인 시작·성공·실패는 이벤트로 계측되어야 한다(constitution 원칙 III —
  측정 기본 탑재). 이벤트 사전에 로그인 이벤트를 추가하고 양쪽 실행 PRD(backend §6.1 ↔
  frontend §8)에 동시 반영해야 한다(원칙 II — 계약 동기화).
- **FR-010**: Google로부터 수집하는 개인정보는 서비스 운영에 필요한 최소한(이메일,
  표시 이름, 프로필 이미지)으로 제한해야 한다.
- **FR-011**: 로그인 도입 이후에도 게스트의 핵심 기능(음악 검색·결과 조회) 이용은
  변함없이 가능해야 한다(constitution 원칙 V — 게스트 우선).

### Key Entities

- **사용자 계정**: Google 인증으로 식별되는 서비스 이용 주체. 이메일·표시 이름·프로필
  이미지를 가진다. 동일 인물은 항상 하나의 계정으로 수렴한다.
- **프로필**: 서비스 내 사용자 정보. 최초 로그인 시 자동 생성되며(기존 프로필 체계
  재사용), 리뷰 유예 상태 등 서비스 상태를 보유한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 신규 사용자가 로그인 화면 진입부터 로그인 완료까지 30초 이내에 도달한다
  (입력해야 하는 가입 폼 0개).
- **SC-002**: 로그인 시도 대비 성공률 95% 이상(계측 이벤트로 산출, 사용자 취소 제외).
- **SC-003**: 동일 사용자의 반복 로그인에서 중복 계정 발생 0건.
- **SC-004**: 로그인 취소·실패 후에도 사용자가 게스트로서 검색을 계속할 수 있는 상태로
  복귀한다(복귀 실패 0건).
- **SC-005**: 운영 배포 환경에서 실사용자 로그인 E2E 검증을 통과한다(로컬과 운영의
  로그인 동작 동일).

## Assumptions

- 인증은 프로젝트가 이미 채택한 위임형 인증 기반을 재사용한다(constitution 원칙 V —
  자체 로그인 플로우 구현 금지). "OAuth2를 붙인다"는 요구는 이 인증 기반의 Google
  제공자 활성화와 연동 완성으로 충족한다.
- 동일한(제공자가 검증한) 이메일을 쓰는 기존 계정이 있으면 별도 절차 없이 같은 계정으로
  자동 연결된다.
- 이메일 로그인(PRD 확정의 다른 한 축)은 본 기능 범위 밖이다. 로그인 화면은 당분간
  Google 단일 수단으로 운영한다.
- Naver 등 추가 소셜 제공자는 범위 밖이다(수요 확인 시 후속 — PRD §3 확정).
- 로그인 화면·버튼 UI는 이미 존재한다. 본 기능의 범위는 이를 실제 동작하게 만드는 것과
  복귀 흐름·오류 처리·로그아웃·계측의 완성이다.
- 대상 환경은 로컬 개발 환경과 운영 배포 환경(프론트·백엔드 배포본) 모두이며, 두 환경의
  로그인 동작은 동일해야 한다.
- 녹음·검색 등 로그인과 무관한 기존 기능의 동작 변경은 범위 밖이다.
